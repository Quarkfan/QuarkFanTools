# QuarkfanTools 3.0 Current Release

Last updated: 2026-08-16

## Release position

This is the first deployable QuarkfanTools 3.0 server platform. The 2.x product is used as a capability and behavior baseline only. No Electron IPC, customer filesystem path, plaintext credential, legacy page structure, or direct cross-layer call is part of the 3.0 contract.

Every migrated ability is exposed through its owning center and uses tenant/Bot identity, durable state, credential references, policy decisions, approvals, audit records and observable execution state as applicable.

## Built-in capability surface

- Playwright deterministic workflows and Model Hub-planned Browser Agent tasks.
- Encrypted reusable browser sessions, external-auth waiting, approval checkpoints, screenshots, PDF, downloads, trace and video artifacts.
- FFmpeg information, trim, merge, resize, crop, rotate, color, audio, text, subtitles, speed, export, compression, thumbnail, normalization, fade, watermark, GIF and blur operations.
- Word, Excel/CSV, PowerPoint and video Skills over governed Resource/Context contracts.
- Lark Sheets range read/batch update and Lark Base record query/batch update. MG owns channel identity and OAuth; CR exposes the capability; writes require governance approval.
- Business templates are packages, never platform-core branches. The hotel check-in planner performs strict unique ID matching, normalization, conflict checks, idempotent update planning and masked output without customer tokens or table identifiers.

## Controlled degradation

- WeCom historical polling from the 2.x desktop CLI is not silently emulated on Linux. Its channel type reports `planned/degraded`; webhook integration is available, and a future remote desktop worker can implement account-bound history polling without contaminating MG.
- The production Lark backend currently uses the Node SDK/OpenAPI implementation. The external CLI adapter is represented honestly as unavailable until its runtime probe and contract suite pass; MG can inject it without changing Message Hub, storage, routing or Console contracts.
- DingTalk remains an explicit unsupported channel descriptor until an adapter is implemented.
- Browser Worker defaults to isolated headless Chromium. Access to localhost/private networks is blocked, including DNS-resolved private addresses. Deployment administrators may explicitly enable private networks for a trusted isolated installation.
- A user's existing desktop Chrome profile is not mounted into the Linux worker. Authentication uses encrypted managed sessions and external-auth waiting.
- Claude Agent SDK execution is available only when its external runtime endpoint and credential are configured. `model-tool-loop` and OpenAI-compatible execution remain available without it.

These are visible capability states, not successful placeholders. They satisfy the platform rule that unavailable host-specific behavior must fail honestly and offer a migration path.

## Designed but not deployed

The next Runtime architecture introduces open Runtime Providers, declarative Runtime Profiles, an append-only Session Event Ledger and one governed capability pipeline. DeepSeek Cordis Core `4.0.1` is exact-pinned behind an incubation PluginKernel with focused contract tests. Existing production adapters still use the current adapter map; no running service behavior has changed. The full DeepSeek Harness is a candidate isolated Runtime Provider, not the platform core.
